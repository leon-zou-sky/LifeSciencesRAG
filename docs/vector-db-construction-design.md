# 生命科学 RAG 向量库构建设计文档

> 目标：从"演示干净数据"升级到"贴近国内药企真实混乱数据"的向量库。
> 本文档定义数据分类、构建顺序、首个分类（医学问询）的详细设计。

---

## 1. 数据分类总表

### A 类：文档（策展式入库，走版本管理，不需要判重）

| Collection | 数据内容 | 来源 | 权威级 | 更新方式 | 维护方 | 真实混乱点 |
|---|---|---|---|---|---|---|
| `drug_inserts` | 本公司产品说明书 | NMPA 批准文件 | A | DMS 审批生效后同步，版本更替 | 注册法规部 | 新旧版本并存（v2023 未作废 vs v2024 现行） |
| `guidelines` | 诊疗指南/专家共识 | 医学会发布、订阅 | A- | 新指南发布入库，旧版标记 | 医学部 | 新旧指南口径不一致（如他汀剂量推荐变化） |
| `clinical_papers` | 临床论文 | PubMed/CNKI 订阅 | B | 订阅管道持续流入 | 医学信息部 | 期刊质量参差、摘要与结论夸大 |
| `competitor_inserts` | 竞品说明书摘要 | 公开渠道收集 | B | 不定期人工收集 | 医学部/市场 | 字段不全、格式不统一 |

### B 类：事件流（流式入库，需要判重 + 人工确认）

| Collection | 数据内容 | 来源 | 权威级 | 更新方式 | 维护方 | 真实混乱点 |
|---|---|---|---|---|---|---|
| `mi_inquiries` | 医学问询记录（问题+答复） | 医生热线/微信/代表转达 | C→B(审核后) | 每条问询流转入库 | 医学信息部 | 口语化、商品名、错别字、一问多药 |
| `case_reports` | 不良事件病例 | 医院上报/热线/文献监测 | C | 每条上报流转入库 | 药物警戒部 | 同一病例多渠道重复上报、表述各异 |

### 分类记忆法

- **A 类回答"知识是什么"**——文档即资产，版本即生命
- **B 类回答"发生了什么"**——事件即流量，判重即质量

## 2. 文档拆块策略（Chunking）

### 2.1 核心原则：按结构拆，不按长度切

生命科学文档有强结构（法定章节/IMRaD/条款），沿语义边界拆，每块语义完整。
通用教程的"每 500 字切一刀 + 重叠 50 字"对这类文档是灾难：

```
错误示范（按字数硬切）：
  chunk A: "...禁与克拉霉"          ← 切断在药名中间
  chunk B: "素、伊曲康唑合用..."     ← 失去主语，不知道是谁的禁忌
```

### 2.2 按文档类型的拆块单元

| 文档 | 拆块单元 | 为什么 |
|---|---|---|
| 说明书 | 法定章节（适应症/用法用量/不良反应/相互作用/禁忌） | 国内化药说明书强制 24 项固定模板，按模板切最干净 |
| 论文 | IMRaD 段落（摘要/方法/结果/讨论） | 摘要密度最高；"疗效数据"命中结果段，"怎么做的"命中方法段 |
| 指南 | 单条推荐意见 | 指南精华是一条条 recommendation，每条自带证据等级（1A/2B） |
| 病例 | 主诉/检查/诊断/治疗/转归 | SOAP 式结构（PoC 已实现） |
| 法规/指导原则 | 条款 | 一条一款，边界明确 |

### 2.3 五个关键技术点

1. **chunk 必须带上下文前缀**——`【药名】【章节】+正文`（见 chunking.py）。没有前缀的"禁与克拉霉素合用"离开原文就是孤儿。前缀把指代焊死在每个块里，检索和 LLM 引用都靠它
2. **块大小 128~512 字**——下界保证语义完整，上界是 BGE 的 512 tokens 截断线。超长章节沿**段落边界**二次切，绝不在句子中间下刀
3. **结构化拆分不需要 overlap**——overlap 是硬切的补丁；沿章节/段落切，每块自带完整语义
4. **表格单独处理**——整表转 markdown 成一个 chunk（PoC 阶段够用）；生产级抽成结构化数据进 MySQL/图谱
5. **元数据与切分同等重要**——每块带 `doc_type/section/authority/version`：检索过滤（只查现行版）、权威加权（A>B>C）、引用溯源全靠它们。**切分决定"能不能搜到"，元数据决定"搜到的可不可信"**

### 2.4 生产级增强（PoC 阶段可不做）

- **父子块（small-to-big）**：小块（200字）做检索提高精度，命中后取父块（整章）喂 LLM
- **问题形式向量**：除原文向量外，再存"这个块能回答什么问题"的向量，提升问询场景命中
- **Reranker 精排**：多路召回后、业务加权前，cross-encoder 对 top-20 重排相关性——专治 6.2 实测发现的双塔高分段噪声；权威维度仍由业务加权层负责，两层正交串联（详见调研文档 2.6①）
- **混合检索（dense+sparse）**：纯向量对病例号/CAS 号/版本号等精确实体不敏感，BGE-M3 sparse 输出 + Milvus 原生混合检索补齐（详见调研文档 2.6③）
- **多语言模型切换**：中英混合文档（进口药说明书）场景评估 BGE-M3，切换走 6.9 蓝绿重建 + 阈值重标定（详见调研文档 2.6②）

### 2.5 方案依据分层

| 层次 | 内容 |
|---|---|
| 有明确出处 | 说明书 24 项模板（NMPA 规范细则）；IMRaD（ICMJE 标准）；指南证据分级（GRADE 体系）；前缀上下文（Anthropic Contextual Retrieval, 2024）；父子块（LlamaIndex ParentDocumentRetriever）；问题向量（HyDE, Gao et al. 2022）；RRF（Cormack et al. 2009）；BGE 512 tokens（模型官方配置） |
| 工程共识 | 按结构拆优于按长度切（LangChain/LlamaIndex 内置结构化 splitter）；向量库是影子索引不是源存储（Milvus 官方定位）；元数据过滤+加权是生产标配 |
| 本项目实测 | BGE 中文分数压缩（无关 0.83 / 同主题 0.87~0.92 / 阈值需实测校准）——前期项目真实数据跑出来的分布 |
| 调参拍的（可调） | 权威权重 A=1.0/B=0.95/C=0.9（初版 0.8/0.6 压没了高相关论文，放宽后平衡） |

## 3. 构建顺序与理由

| 顺序 | Collection | 理由 | 状态 |
|---|---|---|---|
| **① 先做** | `mi_inquiries` | 见下 | ✅ 已完成（判重三档/归一/人工闸/回归全验证） |
| ② | `guidelines` | 补齐 A- 级权威层；结构简单，纯文档拆块，工作量小 | ✅ 已完成（版本作废不进影子，38 块对账一致） |
| ③ | `case_reports` 增强 | 加多渠道重复上报样本，演练三档判重（GVP 法规场景） | ✅ 已完成（向量+四要素混合判重，见第 6 章） |
| ④ | `drug_inserts` 增强 | 加双版本，演练"检索只命中现行版"（version/status 过滤） | ✅ 已完成（改版流程+版本断言，见 6.10） |
| ⑤ 可选 | `competitor_inserts` | 外部数据不完整场景，优先级最低 | ⬜ 待做 |

### 为什么先做 `mi_inquiries`

1. **现在库里只有文档没有流**——3 个 Collection 全是 A 类，事件流是空白，而事件流才是国内场景最乱、最能体现功夫的地方
2. **直接检验归一层**——问询里全是商品名和口语（"立普妥""那个降糖药"），不建归一层检索就废
3. **和 ask.py 形成闭环**——MI 专员接到电话，先查历史问询库"这问题以前答过吗"，答过直接用标准口径，没答过再检索文档起草。这是 MI 真实工作流
4. **和前期知识案例库项目同构**——判重三档、人工确认、增量同步，全是做过的模式，讲得最熟

## 4. `mi_inquiries` 详细设计

### 4.1 Collection Schema

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT64 (PK) | 稳定 ID（内容哈希） |
| `question_raw` | VARCHAR(512) | 医生原始问题（保留口语原文） |
| `question_std` | VARCHAR(512) | 归一后的标准问题（商品名→通用名） |
| `answer` | VARCHAR(2048) | 答复内容 |
| `drugs` | VARCHAR(256) | 涉及药品通用名，逗号分隔 |
| `channel` | VARCHAR(16) | 来源渠道：热线/微信/代表转达 |
| `status` | VARCHAR(16) | draft / approved（审核后才可被检索引用） |
| `authority` | VARCHAR(4) | 初始 C，审核通过后升 B |
| `created_at` | VARCHAR(10) | 日期 |
| `embedding` | FLOAT_VECTOR(1024) | 只对 `question_std` 编码——判重是问题比问题，带上长答案会稀释相似度；answer 作 payload 存储 |

### 4.2 入库管道（数据流）

```
原始问询（口语、商品名、错别字）
   │
   ① 归一层 normalization.py
   │    药品别名表: 立普妥/阿乐 → 阿托伐他汀
   │                格华止 → 二甲双胍
   │                思美泰 → 腺苷蛋氨酸 ...
   │    输出 question_std + drugs[]
   │
   ② 判重三档（阈值经实测标定，现役 duplicate=0.85 / new=0.70）
   │    与库内 question_std 比对 cosine:
   │    ≥0.85  → 重复问题，answer 复用/合并，occurrence+1（无人工）
   │    <0.70  → 新问题，自动立档，状态=draft，answer=NULL（待答复）
   │    0.70~0.85 → 灰色，MI 专员确认"是否同一问题"    ← 人工闸①：判重
   │
   ③ 答复 + 审核（status: draft → approved）           ← 人工闸②：答案
   │    所有新问题都过：筛噪音（无关/错渠道反馈）+ 写首个标准答案
   │    审核前 draft 不进检索——"入得库"和"可被检索"是两件事
   │
   ④ 入 Milvus（upsert 幂等，flush 后才可被搜到）
```

### 4.3 归一层设计（`src/normalization.py`）

```python
DRUG_ALIASES = {
    "阿托伐他汀": ["立普妥", "阿乐", "阿托伐他汀钙"],
    "二甲双胍": ["格华止", "二甲双瓜"],   # 含常见错别字
    "辛伐他汀": ["舒降之"],
    "司美格鲁肽": ["诺和泰", "司美"],
    "华法林": ["华法令"],                 # 错别字
    ...
}

def normalize_text(text) -> (标准文本, 命中药品列表)
def extract_drugs(text) -> list[通用名]
```

要点：先别名映射再 embedding——**归一发生在编码之前**，保证"立普妥"和"阿托伐他汀"在向量空间里是同一个东西，而不是靠模型自己去猜。

### 4.4 样本数据设计（`src/messy_inquiries.py`，12~15 条）

覆盖五种混乱形态：

| 形态 | 示例 |
|---|---|
| 商品名 | "立普妥能和抗生素一起吃吗" |
| 口语化 | "吃那个降脂的药浑身疼是怎么回事" |
| 一问多药 | "格华止和诺和泰能一起用不" |
| 错别字 | "二甲双瓜缓释片怎么吃" |
| 近似重复（测判重） | "阿托伐他汀可以和红霉素联用吗" vs "他汀类降脂药能不能和红霉素一起吃" |

外加 2~3 条**带 approved 答复**的历史问询作为底库，其余模拟新流入。

### 4.5 验证方案（`scripts/test_inquiries.py`）

| 验证点 | 通过标准 |
|---|---|
| 归一正确性 | "立普妥浑身疼" → drugs=[阿托伐他汀]，且检索命中横纹肌溶解相关文档 |
| 判重三档 | 近似重复对落在灰色区间或被正确判重 |
| 权限过滤 | 检索默认只返回 status=approved 的记录 |
| 幂等 | init 脚本重跑，记录数不翻倍 |

## 5. 知识图谱分阶段使用（回顾）

```
阶段1 底库构建:  纯向量库，图谱为空不阻塞
阶段2 事件流跑通: 问询/病例流转时 LLM 顺手抽实体关系 → 图谱逐条积累（副产品）
阶段3 图谱反哺:  边密度足够后支撑三类向量库答不了的查询:
                 ① 多跳机制链（共同代谢酶 → 联用风险）
                 ② 信号关联（反应 × 药物 × 独立来源数）
                 ③ 影响面分析（说明书变更波及哪些关联口径）
```

判断标准：**向量库回答"有什么内容"，图谱回答"谁和谁什么关系"**。

## 6. 实测驱动的设计迭代（①②③ 阶段验证后沉淀）

> 本章只记录**逻辑设计层**的认知迭代——"当初这么设计，实测发现不对/不够，改成那样"。
> 代码实现层的 bug（flush 一致性、子串替换、字符集等）不在此列，见 [rag-engineering-standards.md](rag-engineering-standards.md)。

### 6.1 判重向量只编码判别字段——"什么进向量"是设计决策

**现象**：初版把 question+answer 拼一起编码，几乎原文的重复问询相似度只有 0.8442，跌破 0.85 被判成"新问题"，判重逻辑整体失效。

**设计修正**：编码前先问"这条向量是干嘛的"。判重向量 = 只编码 `question_std`（判别字段）；answer 是展示内容，进 payload 不进向量。修正后同一条 0.9769，三档阈值全部归位。

**沉淀**：**一个用途一根向量，别贪。** 长文本里混进非判别内容，稀释的是你自己的阈值体系。

### 6.2 高分段分数是噪声——排序是业务问题不是算法问题

**现象**：BGE 中文分数压缩在 0.83~0.92 窄带，top3 都 >0.95 时 0.952 vs 0.951 的差异是噪声，按分数排序是自欺欺人。

**设计修正**：分数降级为**召回门槛**；门槛之上的排序交给业务规则——角色画像（热线/医学官/PV 默认视图）> 权威权重 > 版本时效 > 分数。角色配置挂在租户/角色上，不用每次判意图。

**实测效果**：同一查询"辛伐他汀+胺碘酮肌痛"，pv 角色 top5 全是病例、hotline 全是说明书+问询草稿、general 混排；原始分最高的病例（0.8435）在 general 视图被权威权重压到第 4——相关性碾压时低权威能翻身，但默认高权威优先。

### 6.3 纯向量判重不够——病例并案升级两段式

**现象**：③ 阶段病例并案实测：真重复病例 CASE-2024-102 的纯向量分只有 0.8844，落在"不像重复"区间；而不相关的旧病例 CASE-2024-001（也是他汀横纹肌溶解）向量分 0.8591，和真重复几乎拉不开。**纯向量在 PV 判重场景分辨率不足。**

**设计修正**：两段式混合判重——

```
① 向量粗筛（Milvus 影子）：语义找候选
② 结构化精排（MySQL source_meta）：四要素规则打分
   药品集合重合 50% + 发病时间窗 30% + 患者特征 20%
hybrid = 0.5 × 向量 + 0.5 × 规则
   ≥0.87 duplicate 已合并 / 0.78~0.87 gray 人工闸 / <0.78 new   ← 现役值（2026-08-19 重锚，初值 0.90/0.75 错 5/14，见 6.15）
```

**实测效果**：102 被规则分（药品全中+发病差3天+患者吻合=1.00）顶到 hybrid 0.9422 正确并案；103 因发病差 24 天时间窗掉档落灰色带（0.8805）进人工闸。**混合判重的价值就在向量拉不开的那 0.06 分里。**

**推论（为什么四要素必须存源层）**：粗筛命中的旧病例没有结构化四要素，规则打分直接跳过——如果当初把字段只塞进影子 payload，规则层就断了。**检索用影子、规则用源**，两库各司其职。

### 6.4 状态机即检索资格——比过滤器更根本的防线

**现象**：② 阶段的作废指南、③ 阶段的已合并/草稿病例，都不能出现在检索结果里，但都必须留档审计。

**设计修正**：不靠查询侧加过滤器兜底，而是**状态机直接决定同步资格**——同步 SQL 硬过滤 `status='现行'`，影子库从物理上就不含非现行内容。查询侧不需要每次记得加 filter，少一个"忘了加过滤"的事故面。

**实测效果**：影子 38 块 = MySQL 现行 38 块逐块对账一致；作废 2016 指南、已合并 102、草稿 103 零泄漏。

### 6.5 召回天花板——排序救不了库里没有的东西

**现象**：角色视图测试中，用户问"辛伐他汀"，hotline/general 的 top1 都是**阿托伐他汀**说明书——库里根本没有辛伐他汀说明书，BGE 只能召回"最像的同类药"。排序策略再精妙也救不了覆盖度缺口。

**设计修正（三层解法）**：

| 层 | 机制 | 状态 |
|---|---|---|
| 事前发现 | **覆盖率对账**：问询/查询日志的药品通用名 vs 说明书库 drug_name 差集 → 缺口告警（`check_coverage.py`） | ✅ 已验证 |
| 事中降级 | 查询药无 A 级命中时结果区明示"⚠️ 暂无本品说明书，以下为同类药参考"——诚实降级 > 静默给最像的（query.py 内置） | ✅ 已验证 |
| 事后补库 | 缺口 → ingest 管道补采 → 回归门禁 → 生效（链路已具备） | ✅ 已验证（辛伐他汀补库闭环） |

**实测闭环**：对账发现 6 缺口 → 补采辛伐他汀说明书（ingest 5 块）→ 回归 9/9 零漂移 → 同查询 top5 从"阿托伐他汀类药参考"变"辛伐他汀说明书霸榜" → 对账收口 6→5。剩余缺口（红霉素/胺碘酮/华法林）是联用药物非本公司品种，属正确告警——生产上缺口清单需再过一道"是否本公司品种"筛子。

### 6.6 探针必须走完整生产路径——质检本身也有路径一致性问题

**现象**：回归第一版当场抓到 4 项失败——探针绕过归一层直接编码原始输入，测的不是生产路径，门禁形同虚设。

**设计修正**：探针/查询/入库三处强制调用同一个 `normalize_text()`，黄金集断言分三类（归一断言/档位断言/漂移断言）。**"入库"和"生效"是两件事，回归过了才算生效。**

### 6.7 阈值是实测标定的——换模型全库重标

**现象**：判重阈值 0.93/0.85、并案阈值 0.90/0.75 全部来自 BGE-large-zh 在当前数据分布上的实测标定，无任何外部出处。

**设计修正**：阈值单点化到 `config/thresholds.yaml`（全脚本经 `src/thresholds.py` 读取，含模型路径同源），模型升级走蓝绿重标定。**2026-08-17 已用 bge-small-zh-v1.5 实演全程并通过**：`rebuild_shadow.py` 建 512 维影子 → `calibrate.py` 三模型对比标定（24 对标注集）→ 阈值初值 0.80/0.60 经回归终审修正为 0.85/0.70 → 别名切流 → `regression.py --rebaseline` 重录基线（9 探针全过）。实测记录与"标定定初值、回归定终值"的偏差分析见模型文档附录 C。这也是国产化模型替换（Claude/Bedrock → 国产模型）时的安全网。

### 6.8 判重基准池必须纯净——draft 不能当判重依据

**现象**：① 阶段判重测试时，探针撞上了刚 upsert 的 draft 测试行（预期 0.95+ 撞底库，实际先撞了 draft）——未审核的内容成了判重基准，等于"拿半成品当尺子"。

**设计修正**：判重搜索硬过滤 `status == "approved"`。**判重池和检索池是同一个池子，都只对 approved 开放**——draft 既不可被检索引用（6.4），也不可作为判重基准。一道状态机，两处硬过滤。

**推论**：判重基准的质量直接决定分流质量——基准池混进一条错的 approved，后续所有相似问询都会被错误合并到它头上（错误自我强化）。

### 6.9 影子重建要蓝绿，不能 drop-first

**现象**：② 阶段一次重建中途崩溃（Collection 没建全，同步跑在半空），旧影子已被 drop、新影子是空的——**drop-first 是非原子操作，中途失败 = 服务真空**。

**设计修正**：

- PoC 简化：drop + create + 全量重同步（可接受，因为影子可从源重建）
- 生产形态：**蓝绿重建**——新建一套 Collection（名字带版本/日期后缀）→ 全量编码同步 → 黄金集在新影子上跑通 → 切流 → 旧影子留观察期再删。任何一步失败，旧影子还在服务

**同族的生产化预留**（PoC 未实现，设计已留位）：多租户（MySQL 加 tenant_id、Milvus 用 partition_key，共享底库 + 租户私有层）；覆盖率告警接工单系统（6.5 的对账脚本输出直接生成补库工单）。

### 6.10 断言维度必须覆盖业务风险——"全绿"不等于"没问题"

**现象**：④ 阶段混乱态实测：v2023 旧版以 0.8081 vs 0.8026 的**噪声级分差**抢下 top1，而此时探针的来源断言（都是"阿托伐他汀钙片"）和漂移断言（漂移 0.0055 < 容差 0.03）**全部通过**——过期口径穿着绿马甲溜进门。

**设计修正**：黄金集新增**版本断言**（expect_version）：top1 不仅要是正确的文档，还必须是正确的版本。断言维度从"分数/来源"扩展到"版本/状态"——**断言要对着业务风险设计，不是对着方便度量设计**。

**实测闭环**：混乱态回归精确报"期望 v2024.03 实际 v2023.01，过期口径泄漏"→ 改版流程（标作废+影子摘除 5 块）→ 回归全绿且基线 0.8026 分毫不差（摘除精准零误伤）。

### 6.11 融合排序：加权分 vs RRF——两个策略解决的不是同一个问题

**问题**：多路召回后怎么融合排序？业界常提 RRF（倒数排名融合），本 PoC 用的是加权分融合（`final = score × 权威权重 × 角色 boost`）。是不是该换成 RRF？

**先说本质**：RRF（`Σ 1/(k+rank)`，k≈60）**只看名次不看分数**，设计目标是融合**分数尺度不可比的多个检索通道**（BM25 的 12.3 和向量的 0.87 没法直接比）。而本 PoC 当前是**单通道**——4 个 Collection 同一 BGE 同一归一化，分数天然可比。**RRF 要解决的核心问题现阶段不存在。**

**诚实对比**：

| 维度 | RRF | 加权分（本 PoC） | 占优方 |
|---|---|---|---|
| 解决的问题 | 多通道尺度不可比 | 单通道+业务维度 | 各管各的 |
| 分数幅度信息 | 丢弃（rank1 不管 0.95 还是 0.83） | 保留 | 加权分（见下） |
| 业务维度（权威/角色） | 无天然位置——权威是**文档属性**不是**列表** | 原生支持 | 加权分 |
| "相关性碾压能翻身" | 做不到——两列表的 rank1 在 RRF 里打平 | 0.95×0.9 > 0.83×1.0，C 级高能翻 A 级 | 加权分 |
| 调参负担 | 零 | 权重手拍校准 | RRF |
| 换 embedding 模型 | 免疫（rank-based 尺度无关） | 全库阈值重标（6.7） | RRF |
| 配合阈值/漂移断言 | 做不到（断言要的就是分数） | 原生配合 | 加权分 |

**最要害的是第三、四行**：融合层的核心设计语义是"同等相关时高权威优先，相关性碾压时低权威能翻身"。RRF 的 rank-only 特性恰好把这个语义抹掉了——病例列表第一名和说明书列表第一名在 RRF 眼里平等，哪怕一个 0.95 一个 0.83。**在当前架构里 RRF 不是"更标准"，是不适用。**

**实测业务例子**（③ 阶段角色视图验证的真实数据）：

热线场景——医生来电："病人吃辛伐他汀，又开了胺碘酮，现在肌肉疼。"专员查"辛伐他汀 胺碘酮 肌痛"，各库第一名：

| 来源库 | 文档 | 权威级 | 原始分 |
|---|---|---|---|
| drug_inserts | 辛伐他汀说明书·相互作用章 | A | 0.8302 |
| case_reports | 病例 CN-2024-0816（同组合→横纹肌溶解） | C | **0.8435（全场最高）** |
| guidelines | 他汀类药物使用指南 | A- | 0.8210 |

- **RRF**：三个库各自 rank1，`1/(60+1)` **三者打平**——0.013 的分差它看不见，A/C 权威差异它没有概念。对外答复用哪条，抛给运气
- **加权分（实测结果）**：说明书 0.8302×1.0=0.8302 第 1，指南第 2，病例 0.8435×0.9=0.7592 压到第 4。专员对外答复必须念 A 级法定口径，病例是内部参考（知道出过事、语气更谨慎），绝不能对着医生念"我们库里有个病例"——**这个顺序就是合规本身**

反面场景——问"司美格鲁肽会致急性胰腺炎吗"，说明书无相关内容：说明书 0.8310×1.0=0.8310，胰腺炎个案病例 0.9520×0.9=0.8568 **翻身第 1**。0.12 的碾压就该让 C 级上来。而 RRF 对"差 0.013 的噪声"和"差 0.12 的碾压"输出完全相同——都打成平手。**加权分保留了"赢多少"，业务上噪声领先和碾压必须区别对待。**

RRF 的正确工位举例（混合检索上线后）：PV 专员拿病例号查重"CASE-2024-102 类似的报告"——sparse 通道精确命中得分 12.3，向量通道语义命中得分 0.87，**两个尺度没法比，这才是 RRF 的活儿**。

> 数据诚实标注：上表中**实测值**是病例 CN-2024-0816 原始分 0.8435 全场最高、加权后在 general 视图落第 4；说明书/指南的具体分数为示意值（量级符合 BGE 压缩带实测分布）。反面场景（司美格鲁肽胰腺炎）为构造示例，用于说明"碾压翻身"语义。

**坦诚清单（本方案的三个真实弱点，不隐瞒）**：

1. **权重是拍的**——A=1.0/B=0.95/C=0.9 无理论依据（调研文档出处分层照实标注）。生产正解：权重做成配置项，用专员采纳率数据回归校准
2. **乘法放大噪声**——score 高分段本身是噪声（6.2），再乘两个系数，0.95×0.9 vs 0.90×1.0 可能是纯噪声却翻转排序。缓解就是 6.2 的既有设计：分数只当门槛，门槛之上靠业务规则+Reranker
3. **模型迁移成本高**——换模型全库重标，RRF 免疫。这是为"保留幅度信息"付的税

**推广：RRF 的适用边界（不是所有场景都该用 RRF）**：

| RRF 效果好（假设成立） | RRF 不适用甚至有害（假设打破） |
|---|---|
| 多通道、尺度异构（BM25+向量+图谱） | 单通道同模型，尺度可比——扔名次=扔信息 |
| 各通道质量相当，民主投票合理 | 头部集中尾巴是垃圾的通道会污染结果 |
| 分数不可信/无校准条件 | 业务需要"赢多少"的语义（碾压翻身/噪声压平） |
| 冷启动零调参 | 要配合阈值体系（判重三档/漂移断言要分数） |
| —— | 有文档级业务维度（权威/角色是文档属性不是列表属性） |

**方法论**：RRF 的隐含假设是"各通道平等且分数不可信"——本 PoC 场景两条都不成立。所以选型逻辑不是"业界用 RRF 所以我也用"，而是**先看自己的场景满不满足工具的前提假设**。

**生产形态：不是二选一，是串联**：

```
dense + sparse 双通道召回
  → RRF / WeightedRanker 通道融合   ← RRF 的正确工位（混合检索进来后才有活）
  → Reranker 精排相关性（top-20）    ← 修噪声段分辨率（2.4/调研 2.6①）
  → 权威 × 角色业务加权             ← 本 PoC 策略，管合规偏好
```

再往后坦诚到底：规则融合的终局是 **Learning-to-Rank**（用真实点击/采纳数据学排序），但 LTR 要标注数据量，冷启动阶段规则融合是对的——想到终局，但不被方法论绑架。

**设计立场（坦诚版）**：本 PoC 未采用 RRF，原因是其要解决的问题（多通道尺度不可比）现阶段不存在，而核心设计语义（相关性碾压能翻身）恰恰是 RRF 抹掉的信息。本方案的弱点同样明确记录：权重为经验校准值、乘法放大噪声、换模型需全库重标——因此分数只当召回门槛，门槛之上排序靠业务规则，噪声段留待 Reranker 精修。混合检索上线后，RRF 将在通道融合层引入，与业务加权是串联而非替代关系。权重校准与融合层均为可插拔配置，可按评审意见调整。

### 6.12 查询编码要分对称/非对称——判重与检索不能用同一种编码

**现象**：BGE 官方推荐短查询→长段落的非对称检索时，查询侧加指令前缀（"为这个句子生成表示以用于检索相关文章："），官方评测检索准确率提升 1~2 个点。但判重是"问题 vs 问题"的对称比较，单侧加前缀会破坏对称性（两侧语义坐标系错位，同义问法分数反而失真）。

**设计修正**：按数据类型分库的架构红利在此兑现——`src/encoding.py` 提供两个入口：`encode_symmetric`（裸编码，判重/标定用）与 `encode_query`（加指令前缀，仅文档四库查询侧用）。文档入库侧永远裸编码（否则与库内历史向量不可比）。切换后文档探针基线随 `--rebaseline` 重录（分数刻度微移，属预期漂移）。

### 6.13 LLM 生成层：资格闸先行，grounded 起草，引用可机检

**定位**：辅助模式——LLM 只起草，医学信息专员复核后才发出。没有自动应答档，这不是功能缺失，是验证能力边界决定的（见 G-07）。

**管道五种终态**（`scripts/answer.py`，disposition 全部留痕）：

```
问题 → ① 判重短路：命中 approved 标准答案（≥duplicate 线）→ 直接回，LLM 不出场
     → ② 资格闸：top-K 最高原始分 < generation.draft_min_top1（0.60）→ 管道判拒，LLM 不出场
     → ③ 覆盖缺口：药品无 A/A- 原文 → 不起草，明示升级
     → ④ grounded 起草 → 引用校验 → 不过则带错误反馈重试（≤2 次）
        → 通过：draft_passed 交人复核 / 模型拒答：insufficient_evidence / 重试耗尽：draft_failed_human
```

**为什么资格闸是主防线（ANS-03 教训，2026-08-18 实测）**：负对照探针"连花清瘟胶囊可以治疗流感吗"（库中零资料）首跑时，qwen3:4b 凭参数知识硬答，且【1】~【5】引用形式全部合法、引用校验全过——**形式合法 ≠ 语义忠实**，让 LLM 自判"资料够不够"是把守门责任交给最不可靠的环节。修复分两层：prompt 加强（gp-1.1，主题无关也拒答+示例，软约束）+ 检索分数资格闸（确定性硬约束）。与判重短路同一架构哲学：**LLM 只在已验证有资格的场景出场**。

**闸线标定（2026-08-18 重锚 0.50→0.60，G-05 关闭）**：初值 0.50 仅压一条负样本，10 探针分层测量（scripts/measure_gate.py + config/gate_calibration.json）立即暴露漏网——完全无关类 4 条实测 0.4437~0.5431，3 条越过 0.50。**漏网形态值得记录**：用法用量类问题（"奥司他韦怎么吃"）的句式与说明书用法用量章节文体相似，向量撞的是形式不是内容，分数天然偏高。而 should-pass 层（部分重叠/邻近主题/药在库题在库外）实测最低 0.6460，两类间空档宽 0.10，取 0.60。**设计分工由此明确**：闸只拦"全书架空"；部分重叠（一药在库一药库外）过闸是设计内行为——在库药资料为真，LLM 应明示库外药无资料（prompt 铁律 3 兜底）。ANS-04 闸卫探针（取漏网最高分布洛芬）固化该行为进冒烟集。

**引用校验（`src/citation_check.py`）**：能机检的全机检——拒答标记断言、引用存在性、编号合法性（编造不存在的编号=幻觉的可探测形态）、草稿后缀完整性（辅助模式边界标记）。检不了的（句子是否忠于引用原文）留给人——这是"草稿需复核"后缀和签字页永远存在的根本原因。

**配置治理**：模型（qwen3:4b 本地 Ollama，数据不出本机）/temperature=0/重试上限钉死在 `src/llm.py LLM_CONFIG`，prompt 模板带 `PROMPT_VERSION`（改动必须递增）；trace（`data/traces/answers.jsonl`，只增不改）记录模型 digest、prompt 版本、检索编号清单、校验结果、终态——历史答复可复现到配置级。生产化时 JSONL 下沉 MySQL 审计表，字段已按审计表设计。

**为什么不用 LangGraph**：本版是线性管道 + 有界重试环，确定性代码路径本身就是可验证性（审计能逐行讲清控制流）。多轮澄清/工具调用这类真分支循环进来时再评估，届时作为新依赖走变更控制。

**验证状态**：冒烟探针 3 条（ANS-01 判重短路 / ANS-02 正常起草 / ANS-03 拒答负对照）全绿（2026-08-18），冒烟级暂不进 PQ——4B 模型行为长尾波动待 trace 积累稳定性证据，达标后升格（G-06）。

**架构定位**：判重从"单模型一票"变成"向量+规则双签"。与资格闸（6.13）、状态机过滤（6.5）同属一个原则：**确定性机制为概率性机制的自动动作兜底**。黄金集新增一字之差探针断言该行为（任何模型刻度下永不自动判重）。

### 6.14 药品集合规则护栏：向量判重的"双签"机制

**问题**：一字之差难负样本（红霉素→克拉霉素）语义结构同构，余弦 0.9585——duplicate 线压不过它，否则真重复的同义改写也会被错杀。这是表征学习的固有极限，标定章节已证明；本节是它的工程闭环。

**机制**（`src/dedup_guard.py`，全项目唯一判重判定入口 `classify()`）：
- score ≥ duplicate **且**药品集合不一致 → 强制降灰色带（人工闸），永不自动判重
- 护栏只拦不抬：不把低分提拔为 duplicate，只否决向量的"自动"资格
- 任一侧无药品名 → "unknown" 无法裁决，维持向量判定不干预（泛化问题护栏无权发言）

**为什么"标准答案是否相同"可交给药品集合裁决**：MI 问询的答案内容主要取决于涉及哪些药——药品集合不同，答案几乎必然不同；集合相同（同义改写/商品名/错别字），才是真的同一问。归一层已经把商品名/错别字映射成通用名，所以集合比对是纯字典操作，零误差零延迟。

**四个判重点全部走同一 classify**：ingest（CSV 台账自动合并，最高危：直接 UPDATE 计数）、answer（标准答案短路，发错药答案）、test_inquiries（展示）、regression（终审断言——测的就是上线后真实行为，不是裸分数映射）。

**架构定位**：判重从"单模型一票"变成"向量+规则双签"。与资格闸（6.13）、状态机过滤（6.5）同属一个原则：**确定性机制为概率性机制的自动动作兜底**。黄金集新增一字之差探针断言该行为（任何模型刻度下永不自动判重）。

### 6.15 病例并案标定：规则缺项比阈值偏差更致命

**背景**：case_report 的 duplicate/gray 两条线（初值 0.90/0.75）是凭直觉拍的，G-01 挂账待标。2026-08-19 建 14 对分层病例标定对（`config/case_calibration_pairs.json`：应并案 4 / 合法灰色带 3 / 应独立 7 含难负样本，标注经人工评审），`scripts/measure_case_gate.py` 复刻生产打分路径实测——**初值错 5/14**。

**关键发现：5 道错题里 4 道不是线画错了，是规则本身缺项**——

| 错题类型 | 实测 | 病灶 |
|---|---|---|
| 同患者同药同天但事件不同（皮疹 vs 横纹肌溶解） | 规则分满分 1.0，hybrid 0.88 落人工闸 | **不良事件压根没参与规则打分**——药品+时间+患者全满，事件不同也拦不住 |
| 性别不符（女 68 vs 男 72） | 规则分 0.8，hybrid 0.81 落人工闸 | 性别不符只清零患者项（权重仅 0.2），其余满分照样抬过 gray 线——**不同患者必然不同病例，应是硬否决** |
| 药品零重合（度拉糖肽 vs 司美格鲁肽） | 规则分 0.5 偏高 | 问询侧 dedup_guard 的药品护栏思想没接到 case 侧 |

**修复：规则前置三道硬否决**（`init_cases.rule_score`，命中任一即 0 分）：性别不符 / 事件不符（结构化字段比对，互相包含算同，生产应由 MedDRA 编码归一后精确比对）/ 药品零重合。**教训与 6.14 同源：向量抬得动的分数，必须让确定性规则有权一票否决**——四要素是法规要素，不是加权项里的普通特征。

**定线**（否决修复后分布）：merge 0.8995~0.9190 / gray 0.7871~0.8481 / new ≤0.7642（被否决对 ≤0.42），两处空档取中 → **duplicate 0.87 / gray 0.78**（证据注释在 thresholds.yaml）。标定对固化为断言探针 `scripts/test_cases.py`（G-02 关闭，冒烟级，与 test_answers 同定位）。

**方法论复用确认**：这是第三次走通同一闭环——拍脑袋初值 → 分层标定对实测 → 分布空档定线 → 断言探针固化（问询阈值 → 资格闸 → 病例并案）。CP-13 余量仅 0.007，样本仍薄，badcase 只增不改持续扩充（G-03）。

### 6.16 部分重叠问题的双层兜底：词典能认的归管道，认不出的归模型

**验证发现**（2026-08-19，③）：一药在库一药库外的联用问题（"二甲双胍和布洛芬能一起吃吗"）过资格闸后，实测由 LLM 拒答守住（"资料均不涉及布洛芬"）——行为正确，但守门的**不是确定性管道**：coverage_gap 检查依赖别名表识别药名，而布洛芬当时不在表里，检查对它天然是盲的。若 LLM 硬答，引用校验拦不住（引用在库内块完全合法——ANS-03 形态）。

**修复**：别名表定位澄清为**药名识别词典**（不是库内药品清单），补收常见库外药（布洛芬/奥司他韦/连花清瘟，与既有的克拉霉素/阿奇霉素同例）。此后部分重叠形成双层兜底：

| 层 | 覆盖 | 终态 | 探针 |
|---|---|---|---|
| 确定性层 | 词典认识的库外药 | coverage_gap（不起草，明示补库） | ANS-05 |
| 模型层 | 词典不认识的库外药 | insufficient_evidence（模型拒答点名缺药） | ANS-06 |

**为什么缺一半不起草**：联用问题的核心价值在两药相互作用，"在库药没事+库外药无资料"的半截草稿有被读成"可以联用"的误读风险——与 PV 判重"假并案比假独立严重"同属代价不对称逻辑。词典永远列不全天下药名，模型拒答层不可撤——两层都在才是纵深防御。

### 6.17 阈值下沉数据库（BYOM）：调参不走代码部署，变更强制留痕

**动机**：阈值在 yaml 里时，每次调参 = 改代码 + 重新部署 + git 留痕——业务侧（PV 负责人想收紧灰色带）做不到自助。下沉 MySQL 后调参是数据操作不是发版，这就是 BYOM（Bring Your Own Model/配置自持）的配置面。

**三件套**：
- `threshold_config` 表 = 运行时事实源（当前值）；`threshold_history` 表 = 审计（只增不改：谁/何时/旧值→新值/理由）
- 读：`load_thresholds()` DB 优先、yaml 兜底（DB 不可用时回退并**大声警告**，防"改了 DB 脚本还在读 yaml"的静默不一致）；14 个调用方零改动——单一入口设计的红利
- 写：`scripts/set_threshold.py --key --value --by --reason` 四要素强制齐全；合法键注册表防手滑造孤儿键；改完提示重跑回归（**工具管改不管"改得对"，对不对由标定+回归回答**）

**yaml 的新角色**：新环境种子（init_thresholds.py 引导入库）+ 离线兜底。这与"单一事实源"不矛盾——事实源从文件迁到表，种子只是引导材料。

**GxP 映射**：变更控制三要素（谁/为什么/何时）由工具强制；历史表满足审计追溯；运行时阈值冻结不变（进程内缓存，重启生效）——同一输入同一输出。

## 8. 验证文档层（GxP 验证包）

> 第 6 章解决"系统做得对不对"，本章解决"怎么向审计证明做得对"——
> 把代码+配置+输出日志包装为正式验证文档。方法论谱系（V 模型 IQ/OQ/PQ、SR 11-7、GAMP 5/CSA）见调研文档 2.7；逐条业务场景的可审计能力对照见 docs/validation/README.md。

### 8.1 目录命名与含义

```
docs/validation/
├── README.md            验证包总说明 + 业务场景×可审计能力对照表
├── RTM.md               Requirements Traceability Matrix（需求可追溯矩阵）
│                        + Deviation Log（已知缺口登记 G-01~G-04）
├── templates/           受控模板（人工维护，改动即模板版本变更）
│   ├── 00_plan.md       验证总计划：范围/引用文件/通过标准
│   ├── 01_IQ.md         Installation Qualification 安装确认
```

### 8.2 每个文件对应哪个验证环节的证据

| 文件 | 环节 | 证据内容 | 证据来源 |
|---|---|---|---|
| RTM.md | 全程 | 12 条需求 → 设计出处 → 验证手段 → 证据位置的闭环映射 | 人工维护（受控） |
| 00_plan.md | 验证启动 | 验证类型/触发原因/通过标准——**先定标准再看结果**（防结果驱动合理化） | 模板 + 生成器填触发信息 |
| 01_IQ.md | 四级门禁③ 配置一致性 | 环境组件版本、**模型权重 SHA-256 指纹**、thresholds.yaml 快照、三方版本一致性、Collection 行数 | **脚本自动采集**（机器证据） |
| 02_OQ.md | 四级门禁① 标定 | calibrate.py 原始输出归档、三方案建议线、**定线决策表（人工判断点=责任锚点）** | 脚本归档工具输出；定线理由引自 yaml 注释 |
| 03_PQ.md | 四级门禁② 独立终审 | regression.py 实跑输出 + **exit code**、断言覆盖矩阵（归一/档位/漂移/版本 ↔ 需求编号） | **脚本实跑采集**（非复制粘贴） |
| 04_signature.md | 放行批准 | 三部分结论汇总、缺口确认、四角色签署栏（执行/复核/系统负责人/QA） | **纯人工**——脚本只填通过/未通过事实，"批准"结论永远留白 |

### 8.3 两条设计原则

1. **证据与格式分离**：模板是受控文档（审计对象本身），脚本只填证据段。PQ 证据由生成器实际执行 regression.py 采集并归档原始输出与退出码——证据必须是跑出来的，不能是贴出来的
2. **机器不越过的线**：脚本在 PQ 未通过时 exit 1 并提示"签字页不得签署"，但签字栏永远留人填。拦不住人违规签字——这道线靠流程而非代码（SR 11-7 独立验证原则的诚实落地）
