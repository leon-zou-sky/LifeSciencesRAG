# 双体系设计说明：业务系统 × 验证合规体系

> 本文档是全仓库的**体系总纲**：把系统正式拆成两套独立设计、独立迭代的体系——
> **A. 业务系统**（生产线：每个真实问询走的管道）与
> **B. 验证合规体系**（质量保证：不产出答复，但没有它答复不许出厂）。
> 拆分依据：GxP 对"验证逻辑不得混入业务逻辑"的要求；两套体系物理分离、
> 接口受控、变更各自留痕。本文档只定义体系结构与治理规则，具体实现细节
> 一律引用既有文档，不复制内容（单一版本原则）。

---

## 1. 为什么必须分两套体系

制药厂的检验员不能是操作工——自检自验的系统在审计面前说不清
"这段代码是在干活还是在给自己打钩"。对应到本系统：

- **业务系统**回答"问题怎么答"：检索、起草、断言、路由到五个终态；
- **验证合规体系**回答"怎么证明答得对、且一直在对"：探针回归、阈值对账、
  证据采集、缺口登记、人工签字。

两者共用同一条管道（探针跑的就是生产路径，见设计文档 6.6"探针必须走完整
生产路径"），但**代码、配置、文档、变更流程全部物理分离**：改业务代码必须
触发验证体系重跑；改验证体系（探针/阈值锚/模板）不动业务行为，但本身受控。

类比（药厂质量体系）：业务系统=生产线；验证合规体系=QA/QC 体系——
不产出产品，但产品出厂必须由它放行。

## 2. 体系 A：业务系统（生产管道）

### 2.1 组成清单

| 模块 | 位置 | 业务职责 |
|---|---|---|
| 采集入库 | `scripts/ingest.py` + `src/` 各 init 脚本 | PDF/CSV/TXT/XML → 拆块 → 编码 → 入库 |
| 问询判重 | `src/dedup_guard.py`（全项目唯一判重入口） | 三档分流 + 药品集合护栏 + 别名归一 |
| 检索底座 | `scripts/query.py` + 权威加权融合 | 角色视图检索 + 版本作废管理 + 覆盖缺口明示 |
| 病例并案 | 向量粗筛 + 四要素规则精排 | 三道硬否决（性别/事件/药品零重合） |
| 生成层 | `src/llm.py` + `scripts/answer.py` | PII 脱敏 → 判重短路 → 资格闸 → 覆盖核对 → JSON 起草 → 五终态路由 |
| 留痕 | `data/traces/answers.jsonl` 等 | 全要素 trace（模型 digest、PROMPT_VERSION、阈值快照） |

### 2.2 业务系统的设计约束（可验证性的来源）

1. **确定性优先**：能用代码判的绝不用模型判——五终态路由、编号越界、
   coverage 一致性都是确定性断言；模型只干"起草"这一件不可代码化的事。
2. **配置钉死**：模型/temperature=0 写死在 LLM_CONFIG；prompt 是受控配置，
   PROMPT_VERSION 随每次修改递增并进 trace（历史答复可复现）。
3. **机器不越界**：语义忠实度（句子是否忠于原文）永远留给人——
   "草稿需复核"后缀由渲染层强制附加，机器不出"批准"结论。

详细设计：[vector-db-construction-design.md](vector-db-construction-design.md)
（第 1~6 章：数据分类、拆块、管道、18 条实测驱动迭代）。

## 3. 体系 B：验证合规体系（QA/QC）

按"什么时候起作用"分三层：

### 3.1 运行时护栏（过程控制，每次问询都在线）

| 护栏 | 位置 | 拦截对象 | ISPE 五层映射 |
|---|---|---|---|
| PII 脱敏 | `src/pii_guard.py` | 隐私进 LLM/检索 | L3 敏感信息筛查 |
| 资格闸 0.60 | answer.py + `src/thresholds.py` | 全书架空问题 | L4 置信度阈值 |
| 覆盖缺口核对 | answer.py + 药名词典 | 词典内缺药联用问题 | L4 |
| 引用断言 | `src/citation_check.py` | 无引用/编号越界/coverage 违反 | L1 引用校验 |
| 药品集合护栏 | `src/dedup_guard.py` | 高分误判重 | L2 规则化检查 |

### 3.2 变更时验证（放行检验，变更触发）

| 验证件 | 位置 | 检验对象 |
|---|---|---|
| 生成层冒烟探针（6 条） | `scripts/test_answers.py` + `config/answer_golden.json` | 五终态路由不变形 |
| 黄金集回归（问询 10 探针/文档探针） | `scripts/regression.py` + `config/golden_set.json` | 检索/判重端到端 |
| 病例并案探针 | `scripts/test_cases.py` | 并案路由（14 对标定背书） |
| PII 对抗探针（20 条） | `scripts/test_pii.py` + `config/pii_probes.json` | 脱敏率 + 误报防线 |
| 标定工具 | `scripts/calibrate.py` / `calibration_report.py` | 阈值初值（OQ 级） |
| 阈值对账 | `scripts/reconcile_thresholds.py` + `config/threshold_anchors.yaml` | 运行态阈值 = 锚定值（只读 DB，不吃 yaml 兜底） |
| 负对照演练 | [drill 文档](drill-customer-calibration-2026-08-25.md) | 闸门本身有效（故意注入坏阈值验证拦截） |

**验证方法论谱系**（详见调研文档 2.7/2.9）：GxP V 模型 OQ/PQ 分层、
SR 11-7 有效质疑（标定/终审分离）、Google ML Test Score、
蓝绿部署、Champion-Challenger、ISPE GAMP AI Guardrails 五层。

### 3.3 文档证据层（合规产出物）

| 产物 | 位置 | 对应药厂概念 |
|---|---|---|
| RTM 需求追溯矩阵 + 缺口登记 G-xx | `docs/validation/RTM.md` | 验证总计划 + 偏差台账 |
| IQ/OQ/PQ 受控模板 + 签字页 | `docs/validation/templates/` | 验证方案/报告模板 |
| 验证包自动采集 | `scripts/gen_validation_pack.py` → `packs/` | 批检验记录（机器采证据，人签字） |
| 阈值变更审计链 | MySQL `threshold_history`（只增不改） | 变更控制记录 |
| runbook 三纪律 | [model-selection-recalibration.md A.6](model-selection-recalibration.md) | SOP：理由栏禁预填 / 对账是收工条件 / 决策表 |

### 3.4 持续验证（时间维度，2026-08-30 落地）

变更时验证只能抓住"有人动了系统"；时间维度的漂移——容器重启后数据异常、
模型文件被动过、阈值被绕开流程改了——只有定期重跑才能抓到。

| 组件 | 位置 | 职责 |
|---|---|---|
| 调度器 | `scripts/scheduled_verification.py` | 五套件（reconcile/regression/cases/pii/answers）依次执行，exit code 即结论，不解析输出文本 |
| 三态总结论 | 同上 | green=全过（exit 0）/ red=有失败（1）/ **incomplete=无失败但有跳过**（2）——skipped≠绿，全绿报告必须意味着每项真跑过 |
| 基础设施前置检查 | 同上 | MySQL/Milvus/Ollama 探测，依赖不可达的套件记 skipped 而非 failed |
| 定时承载 | `scripts/install_daily_verify.sh`（launchd） | 每日 07:23 本地时间；合盖错过唤醒后补跑 |
| 留痕 | `reports/scheduled/verify_runs.jsonl` + 每次全量 log | 证据目录（git 排除），任何一次结论可回放 |
| 告警 | macOS 桌面通知 | **机器只报告"验证失败需人工处置"，不自动重跑/回滚/修阈值**——自动处置动作永远是人发起（4.2 铁律④的延伸） |

> 全部验证脚本的逐件编目（防什么/环境依赖/场景操作手册）见
> [verification-playbook.md](verification-playbook.md)。

## 4. 两体系的接口与治理规则

### 4.1 变更控制：什么算变更、触发什么

| 变更类型 | 举例 | 必须重跑 | 放行条件 |
|---|---|---|---|
| prompt 契约 | PROMPT_VERSION 递增 | 生成层冒烟 6/6 | 全绿 + trace 留痕新版本号 |
| 阈值 | `set_threshold.py`（强制 --by/--reason） | 回归终审 + 对账 | 回归绿 + reconcile 7 键绿 |
| embedding 模型 | 蓝绿重建 | 标定 → 人工定线 → 终审（重标定四级验证门禁） | runbook 全程 + 签字 |
| 业务代码 | src/ 任意改动 | 相关探针全量 | 全绿 |
| **验证体系自身** | 探针新增、锚值调整、模板改版 | 不需重跑业务验证，但本身留痕 | 探针只增不改；锚值改动记理由 |

### 4.2 铁律（违反任一条 = 体系失效）

1. **探针/标定集只增不改**——检验规程受控，改一条历史结论不可复现；
2. **对账是收工条件**——回归输出对阈值不敏感，混合态只有对账能抓
   （2026-08-25 演练事故：漏回滚造成 dup 0.8416/new 0.70 混合态，
   审计链对账才发现）；
3. **理由栏禁预填**——变更理由必须反映事实，预填模板 = 记录造假；
4. **机器不出批准结论**——验证包采集证据，"批准"永远是人签字；
5. **回归绿 ≠ 采纳推荐值**——决策表裁判：margin 余量都可接受时默认保留现役。

### 4.3 版本留痕链（任何历史状态可重建）

```
prompt:  PROMPT_VERSION（gp-x.y，进每条 trace）
模型:    embedding 路径单点化 + LLM digest 进 trace
阈值:    threshold_config（运行时）+ threshold_history（审计）+ anchors（对账基准）
代码:    git
验证件:  探针集 git 受控（只增不改）
证据:    packs/ 归档（exit code + 环境 + 模型 SHA-256）
```

### 4.4 责任-执行分离与风险边界（多客户交付前提）

**责任不可外包，执行可以外包**：纸面上"输出验证归客户"（Veeva 责任分界，
调研 2.9）是法律结构——受监管公司对合规负最终责任；实际上方案设计、
系统开发、验证执行由实施方承担，客户出需求、内部规范、SOP 签批与最终签字。
对应地，验证体系按"引擎通用、方案每客户一份"设计：标定器/对账器/断言器/
采集器跨客户复用，阈值锚、探针集、签字模板是客户专属配置。

**风险边界：开发方担"规格内正确性"，不担"医学判断对错"**。
专业人干专业事、担专业风险——这条边界由设计机制焊死，不靠免责声明：

| 机制 | 焊住的边界 |
|---|---|
| 辅助模式定位：机器只起草不发出 | 发出动作属于持牌专业人员，"草稿需复核"后缀由渲染层强制附加，不可绕过 |
| 机器不出批准结论 | 验证包只采证据，批准永远是客户的人签字（Part 11 责任主体） |
| 拒答/转人工是一等终态 | 系统不确定时路由给人而非硬答——"我不知道"是合法产出，不是失败 |
| 语义忠实度留给人工复核 | 机器断言只覆盖形式可判部分（引用存在性/编号越界），"句子是否忠于原文"明示由人担 |
| 缺口登记（RTM G-xx） | 已知局限（词典外药名依赖 LLM 拒答、语义层靠人）书面披露=风险告知，客户知情接受 |
| 全要素 trace | 误判发生时可重建现场定责：机器缺陷（断言漏判）走变更控制修复；人工复核疏漏走客户 SOP——**留痕是开发方的责任盾牌** |

| 能力 | 状态 | 缺口 |
|---|---|---|
| 运行时护栏五件套 | ✅ 全量在线 | L3 规则版→NER 增强（G-09） |

| 再验证触发器 | ✅ 半自动（2026-08-30，见 3.4） | 每日定时全量验证+三态告警；自动重标定仍由人工发起（有意保留） |
